# Practical implementation of flash-friendly Block DB in Phraser - Caterpillar Algorithm

Developing the ideas presented in [1. Phraser DB - Optimizing Flash Wear and Bit Rot.md](1.%20Phraser%20DB%20-%20Optimizing%20Flash%20Wear%20and%20Bit%20Rot.md)
, let’s review how these principles have been applied in practice in Block Database implemented in Phraser.  
Below, we will not examine the application-specific data model of Phraser, but will describe the basic logic of the block database, which is generic and agnostic of the data stored in it.  
Note that in our implementation, we support block deletion (Soft Delete) using a Tombstone flag for this purpose.

## 1. Structure of Blocks in the Database

As can be understood from the title, the database consists of a sequence of blocks of equal size. This structure is well-suited for placement on flash, as the block size can be made equal to or a multiple of the flash sector size, thus achieving optimal performance of the storage medium.

![DB Block structure.png](DB%20Block%20structure.png)

Logically, a block consists of a header with identifiers and a version, a footer with a checksum, and user data in the middle.

The header contains the following values:
- `BlockId` - a monotonically increasing unsigned int value starting from 1, which we increment when creating new blocks;
- `BlockVersion` - a monotonically increasing unsigned int value starting from 1, which we increment when updating existing blocks or creating new ones. This version is global for all blocks, i.e., it is not specific to any block. Thus, we always see the sequence of changes and which block was modified last.
- `IsTombstone` - a flag indicating whether the block has been deleted or not. If this flag is set for the latest version of the block, we consider the block deleted.

Since the block has a fixed size, the amount of data that can be stored in it is limited by its capacity. The task of storing larger data across multiple blocks is not addressed at this level.

## 2. Operations on Blocks

A basic set of operations is supported: `CREATE`, `READ`, `UPDATE`, `DELETE`.

#### 2.1 `READ`(BlockId)

To read a block by its identifier, it is necessary to know the offset at which this block is located. In our implementation, we maintain a special hashtable with information about the latest versions of the blocks.

```
struct BlockNumberAndVersionAndCount {
  uint32_t blockNumber;
  uint32_t blockVersion;
  uint32_t copyCount;
  bool isTombstoned;
};

hashtable* blockInfos; //key BlockId, value BlockNumberAndVersionAndCount
```
, where the key is BlockId, and the value is a structure with the following fields:

- `uint32_t blockNumber` - the index of the block in the sequence, so the offset of a specific block can be calculated as (DB_OFFSET + blockNumber * BLOCK_SIZE);
- `uint32_t blockVersion` - the version of the block; since in this structure we have blocks with the latest version, the version is, accordingly, the latest for this BlockId;
- `uint32_t copyCount` - the number of copies of the block that exist in the database with earlier versions;
- `bool isTombstoned` - the "Tombstoned" flag: if it is set, the block is considered deleted.

#### 2.2 `CREATE`, `UPDATE` and `DELETE`

For the operations `CREATE`, `UPDATE`, and `DELETE`, the Caterpillar Algorithm is used.

## 3. Caterpillar Algorithm

The Caterpillar Algorithm is an algorithm that addresses the writing issues on flash, as described in 
[1. Phraser DB - Optimizing Flash Wear and Bit Rot.md](1.%20Phraser%20DB%20-%20Optimizing%20Flash%20Wear%20and%20Bit%20Rot.md) 
attempting to evenly distribute write operations across flash sectors while periodically copying data, preventing blocks 
from being stored for an unlimited amount of time without updates, thus preventing bit rot.

The beauty of the Caterpillar Algorithm is that it achieves this in a lazy fashion, in constant time, and requires O(N) memory, where N is the number of blocks.  

The following can be considered as its drawbacks:

- Since redistribution is triggered lazily, the intensity of redistribution depends on the frequency of C/U/D operations and may occur irregularly, meaning there is no guarantee of a maximum time after which a block would be guaranteed to be rewritten/refreshed.
  - In this regard, I would note that in my experience, the RP2040 flash memory held firmware for years without any signs of bit rot, meaning the reliability of the flash itself is high, and practically this is not a significant concern; usually, passwords are created/updated much more frequently than that.
- The main downside is the 2x write multiplication, but all algorithms that provide a lower rate (such as those on SSD controllers) are not suitable for use in lightweight projects due to their complexity and resource requirements (Disclaimer: AFAIK and IMO).

The main principle on which the Caterpillar Algorithm is based is *complementary throwback copy* described in the 
aforementioned document, which is performed before the main write operation, aimed at preventing excessive wear on 
individual flash sectors due to the imbalance of operations on specific blocks; while also copying additional blocks of 
data around, thus preventing bit rot.

Another important property of the Caterpillar Algorithm is its reliability. This algorithm always writes data in an 
append-only mode, never overwriting data in-place, i.e., it uses a more reliable (fault-tolerant) writing methodology. 
If a write is interrupted in the middle (for example, due to power loss), it will not destroy the previous version or
corrupt existing data.

Thus, for any C/U/D operation, we create a new version of the block with changes, while not overwriting the previous 
version of the same block in-place. The `CREATE` operation generates a new block with a new BlockID, `UPDATE` creates 
a new version of an existing block with updated content, and `DELETE` is essentially the same as `UPDATE`, only 
modifying the Tombstoned flag.

The Caterpillar Algorithm has a small storage overhead in the form of a single free block, meaning one of the blocks 
must always be free. Thus, a database with 128 positions will be filled after creating 127 blocks, and the last free 
block will be used for complementary copying (throwback copy). The presence of this free block will allow us to perform 
throwback copy on `UPDATE` in a filled database while maintaining the aforementioned properties of the Caterpillar Algorithm, and after 
`DELETE` of one or more blocks, we will be able to `CREATE` new blocks again.

### 3.1 Throwback Copying Mechanism, High-Level

###
#### 3.1.1 Glossary

`BLOCK_COUNT` - the capacity of the database in blocks.

`MAX_BLOCK_IDX` - `BLOCK_COUNT - 1`

*Last block* - the block with the maximum version.

*To the right* (of BlockNumber) - in the context of searching, sequentially search in blocks with indices   
`BlockNumber+1, BlockNumber+2, ... MAX_BLOCK_IDX`, and if not found, jump to the beginning of the sequence,  
`0, 1, ... BlockNumber-1`, excluding BlockNumber itself.

*Immediately to the right* (of BlockNumber) - `BlockNumber+1`, or if `BlockNumber == MAX_BLOCK_IDX`, then `0`.

*To the left* (of BlockNumber) - in the context of searching, sequentially search in blocks with indices  
`BlockNumber-1, BlockNumber-2, ... 0`, and if not found, jump to the end of the sequence,  
`MAX_BLOCK_IDX, MAX_BLOCK_IDX-1, ... BlockNumber+1`, excluding BlockNumber itself.

*Immediately to the left* (of BlockNumber) - `BlockNumber-1`, or if `BlockNumber == 0`, then `MAX_BLOCK_IDX`.

*Current block* - the block with the maximum version for BlockId, excluding Tombstoned blocks (meaning that a Tombstoned block is not considered *Current*, regardless of its version).

*DB full* - the database contains `BLOCK_COUNT - 1` Current blocks.

*Occupied block* - the block with the maximum version for BlockId, including Tombstoned blocks.

*Free block* - a block with a non-maximum version for BlockId or a block without data.

*Updated block* - contains C/U/D changes that need to be saved.

### 
#### 3.1.2 CREATE / UPDATE / DELETE

To modify data, we perform the following sequence of actions:
1. Form an *Updated block*.
2. If there are not enough *Free blocks* in the database (`UPDATE`/`DELETE` < 1 block, `CREATE` < 2 blocks)
   - освобождаем Tombstone-блоки
3. Find Block numbers `B1`, `B2`, and `B3` (see `#3.3.1`)
4. Obtain an incremented version, **V1**
5. Read the block at position `B1`, update its version to **V1** without changing the content, and save its new copy in `B2` (`Throwback copy`)
6. If the operation is `CREATE`
   - free up Tombstone blocks again, in case of the situation `tombstoned block with 2 copies` (see `#3.3.4`)
   - Update indices for `B2` (see `#3.3.3`)
7. Obtain another incremented version, **V2**
8. Save the *Updated block* at position `B3` with version **V2**
   - Update indices for `B3` (see `#3.3.3`)

*If `double copy optimization` is used, steps 5 and 8 may be swapped in some cases, see `#3.3.1`


### 3.2 Data Structures in RAM

To perform the actions described in 3.1, we need to maintain data structures in RAM to efficiently find BlockNumbers `B1`, `B2`, and `B3`.
We base this logic on the following collections:

- `rb_tree* occupiedBlockNumbers;`
  - A Red-Black Tree containing the numbers of *Occupied blocks*. It is used to find `B1` and `B2`. Finding `B1` takes O(log(N)), while `B2` takes O(N) in the worst case. The time to find `B2` can also be improved to O(log(N)) by adding a second RBTree `freeBlockNumbers`, but in the case of Phraser, this was not critical.
- `hashtable* blockIdByBlockNumber; //key BlockNumber, value BlockId`
  - An index of BlockId by BlockNumber. It allows us to understand a copy of which BlockId is contained at the index of BlockNumber.
- `hashtable* blockInfos; //key BlockId, value BlockNumberAndVersionAndCount`
  - The previously described (in #1) index of block information for *Occupied blocks*.
- `hashtable* tombstonedBlockIds; //key BlockId, value BlockId`
  - An index containing BlockIds for blocks with the Tombstoned flag set.

### 3.3 Detailed Description of the Algorithm

Let’s describe the Caterpillar Algorithm in more detail, including aspects related to the manipulation of the 
aforementioned indices. This will also demonstrate the mechanics of adding and removing elements in the indices, 
including the specifics related to Tombstoned blocks.

###
#### 3.3.1 Finding `B1`, `B2`, and `B3`

- Find `B1` - the nearest *Occupied block* - *To the right* of the *Last block*
  - > For this, we use rb_tree* occupiedBlockNumbers (O(log(N)))
- Define two blocks, `R1` and `R2`, as follows:
  - `R1` - the block *Immediately to the right* of the *Last block*
  - `R2` - the block *Immediately to the right* of `R1`
    - > calculated using simple mathematical operations `(LAST+1) % COUNT`, `(LAST+2) % COUNT`
- *Happy path*: If both blocks `R1` and `R2` are *Free*, we set the values of `B2` and `B3` as follows:
  - `B2` = `R1`
  - `B3` = `R2`
  - ![Copy positions update.png](Copy%20positions%20update.png)
  - (при *Happy path*, за один проход гусеницы по массиву блоков, каждый блок будет записан ровно один раз, что
    является идеальным сценарием)
  - (in the *Happy path*, during one pass of the caterpillar through the array of blocks, each block will be written exactly once, which is the ideal scenario)
- If not, additional calculations will be required
  - Find `B2 candidate` - the nearest *Free block* - *To the left* of the *Last block*
    - > we look for a gap in `rb_tree* occupiedBlockNumbers` (O(N), which can be improved to O(log(N)) by adding a tree of free positions)
  - Then we check whether `B2 candidate` is closer *To the right* of the *Last block* than `B1`
    - (this corresponds to a situation where there are no gaps in the "caterpillar" body in the form of *Free blocks*)
  - If so, we define `B2` and `B3` as in the "Happy Path"
    - `B2` = `R1`
    - `B3` = `R2`
  - Otherwise, we use the following values
    - `B2` = `B2 candidate`
    - `B3` = `R1`
    - ![Copy positions.png](Copy%20positions.png)


- Throwback copying in a *Full Database*
  - The approach remains the same. Notably, when the *Database is full*, it is always true that `B1` == `B3`  
    ![Copy when DB full.png](Copy%20when%20DB%20full.png)


- Optimizing double copying of the same block:
  - Situations may arise where `B0` == `B1`, and at the same time, the same block is copied twice, meaning we miss the 
    opportunity to update another block during the copying process.
  - As an optimization, the following can be done:
    - Since `B0` == `B1`, we calculate a new `B1` as the nearest *Occupied block* - *To the right* of `B0`.
    - If `B0` == `B3`, a special copying order must be applied:
      - First, copy `B0` -> `B2`
      - Then, copy `B1` -> `B3`
      - The following layouts are possible; as can be seen, for all cases where `B0` == `B3`, we change the order of copying:
        ![Copy optimization.png](Copy%20optimization.png)
      - In cases where `B0` == `B3`, we also obtain another incremented version, **V3**, and use it for the 
        Throwback copy, since the next "head" of the caterpillar (*Last block*) should be `B3`.
        - Alternatively, we can swap the versions and use **V1** for the *Updated block* and **V2** for the Throwback block.

###
#### 3.3.2 Procedure for Releasing Tombstoned Blocks

We can safely free a Tombstoned block only if it is guaranteed to have no copies with an incorrect Tombstoned flag value. 
One way to guarantee it is to ensure that there's only one copy, and it has Tombstoned flag set, like its last version.
If there are other copies, the removal of the last Tombstoned version could theoretically lead to the undesirable recovery of the block, as its previous version's copy may have the Tombstoned flag set to false.

To free Tombstoned blocks:

- Iterate through all BlockIds contained in `tombstonedBlockIds`.
- Retrieve information about the block by its BlockId from the `blockInfos` structure.
- If this Tombstoned BlockId has only 1 copy - i.e., this copy with its latest version, we make the decision to free the block.
- If the decision was made to free it, remove the elements for the BlockId key from `tombstonedBlockIds`, `blockInfos`, and `occupiedBlockNumbers`.

The result of this procedure will be that Tombstoned blocks will become *Free blocks*.


###
#### 3.3.3 Procedure of Updating Indices When Writing a New Block at BlockNumber

In this procedure, we update the indices for both the new block that has just been written at BlockNumber and the old block that occupied BlockNumber before and has now been overwritten.

The procedure is as follows:

1. Update the indices for the old block
   - In `blockIdByBlockNumber`, check if the `old BlockId` exists for `BlockNumber`
     - If it exists, remove it from `blockIdByBlockNumber`
       - Retrieve information for the old block from `blockInfos`
       - Decrement the `copyCount` field for the old block, and if it becomes equal to 0, remove the `old BlockId` from `blockInfos` and `tombstonedBlockIds`
       - Remove `BlockNumber` from `occupiedBlockNumbers`


2. Update the indices for the new block
   - Add `BlockNumber` associated with the `new BlockId` in `blockIdByBlockNumber`
   - Retrieve information for the new block from `blockInfos`
     - If it does not exist, create information with `copyCount = 1`
     - If it exists, increment `copyCount` and update the fields `blockNumber`, `blockVersion`, `isTombstoned`
   - Depending on `isTombstoned`, add or remove from `tombstonedBlockIds`
   - Add `BlockNumber` to `occupiedBlockNumbers`


###
#### 3.3.4 The phenomenon of `last tombstoned block with 2 copies`

- This situation arises when, in a *Full Database*, we delete one of the blocks, giving it a Tombstone status.
  Then, the previous version of this block becomes a *Free block*, while its new copy with the updated Tombstoned status 
  becomes the *Last block*; thus, it gains 2 copies.

- If immediately after that we want to take advantage of the freed space by creating a new block, 
  it will not be possible to free this Tombstone block at step `#3.1.2-2`, as it has 2 copies.
  However, since it is the *Last block* and cannot be `B1`, Throwback copying is guaranteed to overwrite its older copy, 
  due to the fact that it's the only *Free block*. As a result, only one copy will remain in the database.
  Given that, at step `#3.1.2-6` we can fully free this Tombstone block, thus providing space for the creation 
  of a new block in the DB.

- As an alternative solution, a "lazy" approach can be used.
  In this approach, we do not check for the presence of just *Free blocks*; instead, we ensure that we have a 
  sufficient total of *Free* and/or Tombstone blocks.
  Then we make the best effort to free Tombstone blocks, and if this does not succeed, we allow the database to reach 
  a state without *Free blocks* but with a Tombstone block after adding a new block.
  Then, the next data modification operation will free this Tombstone block at step `#3.1.2-2`.
  However, using this approach would mean weakening the integrity control of the database and potentially allowing 
  for the possibility of missing other types of inconsistencies. Therefore, preference was given to the explicit 
  freeing of the Tombstone block after Throwback copy at step `#3.1.2-6`.
