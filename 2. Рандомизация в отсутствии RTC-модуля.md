# Рандомизаци значений в отсутствии RTC-модуля

Качественная рандомизация - это крайне важный фактор практически во всех применениях в безопасности, особенно когда речь идет о
генерации секретных ключей, паролей и прочих значений для использования в криптографических алгоритмах.

### Стандартный подход

Классический подход основывается на генераторах псевдослучайных последовательностей, инициализируемых неким случайным значением.
При этом в качестве подобного псевдо-случайного значения зачастую используется значение текущего Unix Time. Можно дать следующие 2
комментария касательно этого подхода.

1. В целом, значение Unix Time, хотя и попадает в довольно широких диапазон, но при этом не является непредсказуемым.
Причем оно тем более предсказуемо, чем более узок диапазон, значения из которого оно может принимать. Например, если вы помните, что дело было
весной 2024-го, или же в марте 2024, или же с 10-15 марта 2024, или же в первой половине дня 14 марта - каждое подобное
уточнение сужает диапазон в разы.
В качестве иллюстрации, рассмотрим широко известный практический пример эксплуатации подобного знания для восстановления
доступа к Биткойн-кошельку, пароль к которому был сгенерирован на основании только лишь текущего времени. 
(см: https://youtu.be/o5IySpAkThg?t=724)  
Как мы видим из данного практического примера, само по себе использование подобного подхода недостаточно рандомно, а потому
недостаточно безопасно.


2. И если это одно недостаточно плохо, Phraser базируется на основе микроконтроллера RP2040, у которого даже нет
Real Time Clock модуля. Практически это означает, что RP2040 не имеет информации о текущем времени с начала unix эпохи,
а может только знать о том, сколько времени прошло со времени последнего старта. Это значение все еще можно использовать
для инициализации генератора псевдослучайных последовательностей, но но оно гарантированно будет находиться
в крайне узком диапазоне.

Таким образом, необходим иной подход, который позволит сделать инициализацию псевдослучайных последовательностей по-настоящему
безопасной, то есть использовать некий более случайный источник энтропии.

### Решение для Phraser

Была использована следующая идея - поскольку Phraser имеет ПЗУ на базе flash-памяти, где хранятся структурированные 
данные в виде блоков, то можно хранить определенные рандомные значения прямо в этих блоках. 
Для этого в структуру наших блоков мы добавили поле entropy, имеющее тип uint32, в котором мы храним инициализационное
значение для генератора (random seed). Учитывая, что все блоки у нас версионированны и существует понятие "последнего блока", т.е. блока
с максимальной версией, который также является последним созданным блоком, а также т.к. каждое изменение в БД порождает
новый блок, для каждого блока мы сохраняем новое случайное значение entropy source/seed в этом поле, а при каждом включении устройства мы инициализируем
генератор с этим значением из последнего блока.

### Инициализация первого блока

Пока что все выглядит неплохо, но каким же образом мы инициализируем первый блок, с сохранением свойства безопасности?

Существует 2 способа, которыми БД может попасть на ваше устройство.

1) Функция `Restore DB`, при которой блоки копируются извне, т.е. значения полей entropy в этих блоках предустановлено.
В "официальном" PhraserManager, написанном на Java для установки этих значений используется 
[SecureRandom](https://docs.oracle.com/javase/8/docs/api/java/security/SecureRandom.html), который мы считаем
в достаточной мере безопасным.


2) Функция `Create DB` - генерация базы данных непосредственно на токене.
В этом случае мы используем комбинацию данных, введенных пользователем, а также количество микросекунд, прошедших
 с момента запуска устройства.  
Конкретнее:
   - при инициализации пользователь указывает пароль БД;
   - также мы дополнительно просим пользователя ввести случайную строку;
   - и используем функцию micros() для получения текущего значения микросекунд;
   - затем от этого всего вычисляем sha256, который XOR-коллапсим в 32-битное целое.
Исходный код для этого выглядит следующим образом:
```
    uint32_t micros_int = micros();
    char micros_str[50];
    itoa(micros_int, micros_str, 10);

    uint8_t digest[32];
    sha2_context ctx;
    sha2_starts(&ctx, 0);
    sha2_update(&ctx, (uint8_t*)new_password, strlen(new_password));
    sha2_update(&ctx, (uint8_t*)random_str, strlen(random_str));
    sha2_update(&ctx, (uint8_t*)micros_str, strlen(micros_str));
    sha2_finish(&ctx, digest);

    uint32_t seed = sha256ToUInt32(digest);
```

### Инициализация генератора псевдослучайных последовательностей 

Для усиления безопасности, мы не просто инициализируем генератор хранящимся в блоке значением, а 
комбинируем его с текущим значением микросекунд и прогоняем через sha-256, способом, 
сходным с вышеописанным в `Create DB`. При этом мы инициализируем генератор "лениво", то есть не при запуске, а при 
первом вызове функции, требующей использования случайности, для получения максимального эффекта случайности от 
прошедших со времени старта микросекунд.

```
    uint32_t micros_int = micros();
    char micros_str[50];
    itoa(micros_int, micros_str, 10);

    char last_entropy_str[50];
    itoa(get_last_entropy(), last_entropy_str, 10);

    uint8_t digest[32];
    sha2_context ctx;
    sha2_starts(&ctx, 0);
    sha2_update(&ctx, (uint8_t*)last_entropy_str, strlen(last_entropy_str));
    sha2_update(&ctx, (uint8_t*)micros_str, strlen(micros_str));
    sha2_finish(&ctx, digest);

    uint32_t seed = sha256ToUInt32(digest);
    randomSeed(seed);
```

### Формирование значений поля entropy для новых блоков

С учетом вышесказанного, когда дело доходит до формирования новых блоков, генератор уже был достаточно безопасно 
инициализирован, поэтому здесь обходимся без изысков.

```
  store_block->entropy = random_uint32();
```

Равно как и в остальных применениях, например, генерация паролей/строк.
