# DB Encryption in Phraser

Let's review how Database encryption works in Phraser.

## 1. Block Encryption

Blocks are encrypted using the AES-256 CBC algorithm.

1. `IV Mask` concept.  
For each block, we use a unique `IV` value.  
This value is computed by XORing two parts: `IV Part` and `IV Mask`.  
`IV Part` is contained in the 16-byte footer of the block and is unique to each block.  
The value of `IV Mask` depends on the type of block as described below.


2. Encryption of `KeyBlock`.  
`KeyBlock` is a special type of block that contains the main `Key` and the main `IV Mask`, which are used for encrypting all other blocks, except for the `KeyBlock` itself.  
`KeyBlock` itself is encrypted with a key derived from the MasterPassword using the PBKDF2 algorithm (`KeyBlock key`), and we use a constant value as the `IV Mask`, corresponding to the MD5 hash of the string "PhraserPasswordManager".

![KeyBlock.png](KeyBlock.png)

3. Encryption of Other Blocks.  
   As it was mentioned above, encryption of other blocks (except for the `KeyBlock`) is done using the main `Key` and the main `IV Mask`, which we obtain from the `KeyBlock`.


## 2. Structure of Blocks

The structure of the encrypted block is as follows:

![Encrypted Block structure.png](Encrypted%20Block%20structure.png)

- The "outer layer" (upper part) consists of 2 parts - 16 bytes in the footer make up the `IV Part`, 
while the rest of the block is encrypted using the method described above.
- After decrypting the main part, the last 4 bytes of the decrypted buffer will contain the value of the Adler32 
checksum computed from the preceding bytes. This allows us to verify the integrity of the block after decryption 
(as shown in the lower part of the diagram).
- Additionally, after decryption, the bytes are arranged in reverse order before the checksum. If we look at the data 
structure, we will see that the tail of unused bytes is filled with random values. Thus, when we reverse this sequence, 
the random bytes move to the beginning of the buffer, preventing a hypothetical cryptanalyst from basing their analysis 
on possible values of the block header.
- After decrypting and verifying the block's checksum, these bytes need to be reversed back to start operations.


## 3. Security Properties

This encryption method helps avoid metadata leakage but requires additional time (2 passes instead of 1) to load the 
database. Thus, without knowing the keys and IV masks for decryption, it is impossible to distinguish encrypted KeyBlock 
from encrypted data blocks or from random data.

In addition, two-level of encryption in combination with PBKDF2 make attacks on the Master Password more 
difficult, as only the `KeyBlock` is encrypted with Master Password, while all other blocks are encrypted with the main 
key stored within the KeyBlock itself. Therefore, without access to metadata, it is impossible to determine where the KeyBlock is 
located, and a hypothetical cryptanalyst would need to significantly increase their work to process all blocks, due to 
use of PBKDF2 to initially form the `KeyBlock key`. In the absence of metadata leaks it's very hard to guess which 
block to focus on, which makes the attacker's task much more challenging.

Furthermore, Phraser allows users to customize the number of PBKDF2 iterations, using their own unique settings for 
each database (`UP` + `A` + `B` on Unseal). If this technique is also applied, then in the absence of any additional data 
about your Master Password, the idea of guessing it becomes largely impractical. By default, Phraser performs 
10,239 iterations, and if we assume that the user can vary this value from 5,000 to 15,000, the attacker would have to 
multiply their efforts by an additional factor of 10,000. However, there is also a cost for the user in using this 
feature, as it involves some inconvenience in manually entering the number of iterations during each unlock.


## 4. Database Decryption Procedure

Given the information stated above, we can see that database decryption steps will be as follows:

1. Request user's Master Password and compute `KeyBlock key` to decrypt `KeyBlock` using PBKDF2 algorithm.
2. Next, we need to read all the blocks of the database to find the latest version of `KeyBlock`. For this, we use 
the key computed in the previous step (`KeyBlock key`) and the constant `IV Mask` for decryption.
3. If we fail to find `KeyBlock`, we cannot load the database. This may happen, for example, if the supplied Master Password is incorrect.
4. Then, from the `KeyBlock`, we obtain the main `Key` and the main `IV Mask`.
5. We iterate through all the blocks of the database once again, now attempting to decrypt them using the main `Key` and the main `IV Mask`.
6. During this process, we populate the caches and indexes of the database with data from the blocks.
7. The database is ready for use!
