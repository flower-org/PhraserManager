# Randomization in absence of RTC-module

Quality randomization is a crucial factor in almost all security applications, especially when it comes to generating 
secret keys, passwords, and other sensitive values for cryptographic algorithms.


### Standard Approach

The classical approach is based on pseudorandom number generators (PRNGs) that are initialized with some random value. 
Current Unix Time value is often used as such a "random seed" value. 
Two comments can be made regarding this approach:

1. Overall, the Unix Time value, while falling within a fairly wide range, is not unpredictable. Moreover, it becomes 
increasingly predictable as the range of possible values narrows. For example, if you remember that the event occurred 
in the spring of 2024, or in March 2024, or between March 10-15, 2024, or in the first half of the day on March 14, 
each of these clarifications significantly narrows the range.

As an illustration, consider the following well-known practical example of exploiting knowledge of the time of the event 
that was used to regain access to a Bitcoin wallet, the password for which was generated based solely on the current time. 
(See: https://youtu.be/o5IySpAkThg?t=724)

As we can see from this practical example, the use of Unix Time as random seed is not sufficiently random and, 
therefore, not secure enough.

2. There is another issue to pile on top of the one described above, specifically, that Phraser is based on RP2040 
microcontroller, which does not even have a Real-Time Clock module. Practically, this means that the RP2040 has no 
information about time since the start of the Unix epoch and can only know how much time has passed since 
it was powered on. This value can still be used to initialize a pseudorandom number generator, but it is guaranteed 
to be within a very narrow range.

Therefore, a different approach is required to make the initialization of pseudorandom sequences truly secure, meaning 
that a more random source of entropy should be used.


### Solution used in Phraser

The following idea was implemented: since Phraser has flash memory in which we store structured data is the form of blocks, 
certain additional random values can be also stored in these blocks. To achieve this, we added an `entropy` field of type uint32 
to the common structure of our blocks, where we store the next initialization value for the generator (random seed).

Considering that all blocks are versioned and there is a concept of the "last block," i.e., the block with the highest 
version that is also the most recently persisted block, and since every change in the database generates a new block, 
we save a new random value as the entropy source/seed in this field for each block. Upon each device power-up, 
we initialize the generator using the entropy value from the last block.


### Initialization of the First Block

So far, everything looks good, but how do we initialize the first DB block while maintaining security properties?

There are two ways in which the database can be created on a Phraser device.

1) When using the `Restore DB` function, blocks are copied from an external source, meaning that the entropy field 
values in these blocks are pre-set. In the "official" PhraserManager JavaFX app, [SecureRandom](https://docs.oracle.com/javase/8/docs/api/java/security/SecureRandom.html) class is used to 
set these values, which we believe provides sufficient secure randomness guarantees.

2) `Create DB` function creates the database directly on the token. In this case, we use a combination of user-entered 
data and the number of microseconds elapsed since the device was powered on.

Specifically:
    - During initialization, user specifies the database password;
    - We also ask user to enter a random string;
    - We use `micros()` function to obtain the current value of microseconds since startup;
    - Then, we compute the SHA-256 hash of all this data and XOR-collapse it into a 32-bit value.

The source code for this looks as follows:
```
    uint32_t micros_int = micros();
    char micros_str[50];
    itoa(micros_int, micros_str, 10);

    uint8_t digest[32];
    sha2_context ctx;
    sha2_starts(&ctx, 0);
    sha2_update(&ctx, (uint8_t*)new_password, strlen(new_password));
    sha2_update(&ctx, (uint8_t*)random_str, strlen(random_str));
    sha2_update(&ctx, (uint8_t*)micros_str, strlen(micros_str));
    sha2_finish(&ctx, digest);

    uint32_t seed = sha256ToUInt32(digest);
```


### Initialization of the Pseudorandom Number Generator

To enhance security, we do not simply initialize the generator with the `entropy` value stored in the block;  
we combine it with the current value in microseconds and run it through SHA-256, in a manner similar to that 
used in `Create DB`. Additionally, we initialize the generator "lazily," meaning that it is not initialized at 
startup but rather at the first call to a function that requires the use of random values. This approach maximizes 
the variability and randomness effect from microseconds elapsed since power-on.
```
    uint32_t micros_int = micros();
    char micros_str[50];
    itoa(micros_int, micros_str, 10);

    char last_entropy_str[50];
    itoa(get_last_entropy(), last_entropy_str, 10);

    uint8_t digest[32];
    sha2_context ctx;
    sha2_starts(&ctx, 0);
    sha2_update(&ctx, (uint8_t*)last_entropy_str, strlen(last_entropy_str));
    sha2_update(&ctx, (uint8_t*)micros_str, strlen(micros_str));
    sha2_finish(&ctx, digest);

    uint32_t seed = sha256ToUInt32(digest);
    randomSeed(seed);
```


### Generating entropy Field Values for New Blocks

Given the above, when it comes to generating new blocks, the generator has already been sufficiently and securely 
initialized, so we can proceed without any additional complexities.

```
  store_block->entropy = random_uint32();
```

Just like in other applications, such as password generation or other words.


### Use of a Secure Random Sequence Generator

Another important factor is the use of a secure random value generator. Currently, Phraser utilizes `Hash_DRBG`, 
for which there is a security proof for generating pseudorandom sequences.

https://en.wikipedia.org/wiki/NIST_SP_800-90A#Hash_DRBG_and_HMAC_DRBG
